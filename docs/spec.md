# moshimoshi 仕様（詳細）

README に入りきらない分をここに置いています。脅威モデル、作法の全文、判定の 4 層、参照構成、評価手順、採用側への宿題。文章は CC BY 4.0。


「もしもし」には、妖怪や狐は「もし」を二度続けて言えないので、人間であることを示すために言った、という俗説がある。電話の最初の一言は、もともと**人間確認の合言葉**だった。この提案は、その役目を AI 時代にもう一度与える。
（Kyutai の音声対話モデル Moshi とは無関係です。）

> **Status: Proposal / RFC (2026-10).** 評価結果はこれから。設計への意見・反例・データ提供を歓迎します。
> **English summary:** *moshimoshi* (named after the Japanese phone greeting, which folklore says was used to prove the speaker was human, since foxes and spirits could not say it twice) is an open specification and reference implementation for detecting AI voice callers (TTS, voice clones, LLM phone agents) during a live phone call. Instead of relying only on passive deepfake-audio detection, which degrades over narrowband telephony codecs, the callee can **put the caller on hold for ~10 seconds** and run a short **active liveness challenge** that is trivial for humans and hard for voice agents (laughing, humming, describing background sounds, answering interruptions). Signals from four layers are fused into a *non-binding* risk score with a one-line reason. We publish the spec (CC BY 4.0), a reference implementation (Apache 2.0) and an evaluation protocol with telephone-grade audio, so that carriers, handset makers and app developers can adopt it. We do not operate a service. Built with Claude Fable 5.1. Commercial use is permitted under the licenses below.

## なぜ作るか
AI 音声による詐欺電話（家族のなりすまし、自動音声の営業・脅し）は増え続ける一方で、受ける側に「相手が AI かどうか」を確かめる手段がない。既存の対策は通話音声を聞いて合成音声の痕跡を探す受け身の方式が中心で、電話の圧縮（8kHz 相当）と合成音声の進歩で効きにくくなる。

この提案（**もしもし確認 / Moshimoshi Protocol**）は **「通話を一時停止して、相手に人間なら簡単な課題を数秒出す」** という作法を定め、判定は補助情報として受ける側に返す。誰でも実装・採用できるよう、仕様・参考実装・評価手順を公開する。

## 想定する攻撃（脅威モデル）
1. **AI 音声エージェントによる詐欺・営業電話。** LLM と TTS がつながった「会話する AI」が大量に発信する。
2. **家族・知人の声の複製によるなりすまし。** 数秒〜十数秒の声があれば複製できる。
3. **声の盗み取り（ワンギリ型）。** 知らない番号から一瞬だけ鳴らして出させ、「もしもし」や名乗りの声を録る。相手は黙っているか、アンケートや間違い電話を装って数文を喋らせる。録った声で本人の声を複製し、その家族や知人に電話する。**攻撃 2 の仕込み段階**であり、ここを塞ぐと複製そのものを減らせる。

moshimoshi は 1・2 を「出口」（受ける側の確認）で、3 を「入口」（自分の声を渡さない）で防ぐ。

## 入口の守り: 自分の声を盗らせない
受ける側が知らない番号に出るとき、確認が済むまで **自分の生の声を相手に渡さない**。
- **代理の声で応答する。** 最初の応答はアプリ（または網）が合成音声で行う。「どちら様でしょうか。ご用件をどうぞ」。本人は相手の声を聞いて判断し、確認が済んでから自分の声で話す。
- **声の変換で出る。** 本人が話すが、相手に届く音声は別人の声に変換する（端末内の軽い声質変換）。確認後に解除。
- **短い無言の着信を警告する。** 知らない番号・数秒・相手が無言、の組み合わせを「声取りの可能性」として記録し、折り返しをしないよう促す。
- **名乗らない既定。** 知らない番号への応答で名前・家族の名前・住所を口にしない作法を、応答の合成音声で代行する。
- **家族の合言葉。** 複製された声で家族にかかってきても、合言葉（D 層）と折り返しで見抜ける。合言葉は電話で言わず、会って決める。

入口の守りは判定モデルに依存しないので、合成音声が進歩しても効く。**「代理の声で応答する」「名乗らない既定」は、下の 2-A 留守電型が最強の形**（自動応答が常に代理で応答し、利用者の生の声は一切相手に渡らない）。

## 作法（利用者から見た流れ）

### 2-A. 留守電型（一次）
1. 知らない番号の着信には**出ない**（1回スルー）。
2. 無応答が続くと moshimoshi が自動応答し、「自動応答です・録音します」と名乗る（利用者の氏名・家族の名前・住所は言わない）。
3. 「どちら様でしょうか。ご用件をどうぞ」と聞き、回答を録音。
4. 数問確認（名乗り／即興の変形／環境音など 2〜3 問・20 秒以内）を行う。
5. 「ご用件は本人にお伝えします」で終話（40〜60 秒で打ち切り）。
6. 判定器が録音から AI の可能性（%・暫定/校正前ラベル付き）＋根拠を出し、着信一覧に積む。
7. 利用者はあとで一覧を見て、録音を聞き、折り返す／無視する／着信拒否にする／家族に知らせる、を選ぶ。利用者の操作はここだけ。

### 2-B. 転送型（第2の形）
1. 通話中、怪しいと思ったら「確認」操作をする。
2. 相手は「本人確認中です。10 秒ほどお待ちください」の保留に入る。
3. 保留中に短い課題を 1〜2 つ出す。
4. 結果を **受ける側だけに**（画面またはささやき音声で）伝える。「AI の可能性: 高・中・低」と理由 1 行。
5. 続ける・切る・記録する・家族に知らせる、を利用者が選ぶ。

2-A が効かない場面（相手が無言で切る・用件を言わず切る緊急の人間）や、採用側（通信事業者・端末メーカー）が網内で保留を実装できる場合は 2-B を使う。

**原則**
- **断定しない。** 判定は補助。最終判断は利用者。
- **理由を見せる。** 「返事の遅れが一定」「笑いに反応せず」のように、何を見たかを 1 行で。
- **人を怒らせない。** 課題は 10 秒以内、丁寧な文言、失敗してもやり直せる。
- **残さない（2-B）／端末内・30日・削除可（2-A）。** 2-B は既定で音声を保存せず、保存は利用者の明示操作のみ。2-A（留守電型）は「判定が外れても録音が残る」ことが利点のため、既定で録音し端末内に 30 日保存・自動削除・いつでも個別削除可とする。条件: ①応答の名乗りで「録音しています」の文言を削らない ②発信者にも利用目的を通知・公表する ③保存期間は有限にする（無期限は不可）。いずれも外部送信はしない。
- **緊急番号には使わない。**

## 判定の 4 層
| 層 | 見るもの | 常時/保留中 |
|---|---|---|
| A 受け身の痕跡 | 合成音声の痕跡（スペクトル、息継ぎ、口腔ノイズの欠如）。電話音質で再学習した検知モデル | 常時 |
| B 会話のリズム | 返事までの遅れの分布、相槌の重なり、割り込みへの反応、文字起こしの予測しやすさ（パープレキシティ）と言いよどみ率 | 常時 |
| C 能動テスト | 人には簡単で音声エージェントには難しい課題。**課題の族**のみ公開し、具体的な課題は実行時に生成する（固定文は学習されるため） | 保留中 |
| D 関係の確認 | 合言葉、登録番号への折り返し、（将来）発信者の電子署名 | 保留中・任意 |

4 層を点数にして統合する。どの 1 層も単独で結論を出さない。

### 能動テストの課題の族（例）
- 身体的反応: 笑う、ため息、ハミング
- 環境の知覚: 「いま背景で何が鳴っていますか」
- 即興の変形: 言われた数列を逆順に、語尾を変えて
- 割り込み耐性: 相手が話している途中で質問を重ね、反応の自然さを見る
- 関係知識: 合言葉、共通の記憶（D 層）

## 参照構成

### 2-A 留守電型（一次）
```
相手 ──電話網──> [自動応答・名乗り＋数問確認] ──> 録音ファイル
                     │ 通話後・ファイル（オフライン）
                     ▼
            [判定エンジン]  A 痕跡モデル / B リズム・テキスト / C 課題の進行役 / D は未実施（合言葉を使わない）
                     ▼
            [着信一覧]  録音の再生＋AI の可能性(%・暫定)＋根拠。利用者があとで確認して選ぶ
```
通話音声にアプリが触れられない（iOS/Android の壁）を、自動応答の録音というファイルの形で迂回する。層C（能動テスト）が常時・毎回効くのが 2-B との最大の違い。

### 2-B 転送型（第2の形）
```
相手 ──電話網──> [通話の入口] ──> 受ける側
                     │ 音声（通話中のみ・メモリ上）
                     ▼
            [判定エンジン]  A 痕跡モデル / B リズム・テキスト / C 課題の進行役（ルール＋TTS、LLM 非依存） / D 関係の確認
                     ▼
            [結果] 受ける側だけに表示・ささやき。保存は既定でなし
```
通話の入口は実装側の自由。本提案は入口を規定しないが、段階ごとに現実的な入口は次の 3 段。

| 段 | 入口 | できること | 制約 |
|---|---|---|---|
| iPhone | 留守電（ライブ留守番電話・ビジュアルボイスメール）の音声を「共有」→ ショートカットが判定エンジンへ送る | 1 件ずつ手動で判定。アプリ不要・審査不要 | iOS は他社アプリが留守電や通話音声を自動で読めない |
| Android | 通話スクリーニング API で自動応答・録音 | 2-A 留守電型を 1 つのアプリで完結 | 実機が要る |
| 通信事業者 | 網側の留守番電話に判定を組み込む | 端末を問わず自動。iPhone でも自動になる | 採用側の実装（下の宿題） |

参考実装は **判定エンジンをサーバ側（自宅 PC で可）に置き、iPhone のショートカットから使う形** から始める。費用ゼロ、公開モデルのみ。

**本プロジェクトはサービスを運営しない。** 判定エンジンは誰でも自分の PC・NAS・自社サーバで動かせる形（コンテナ）で配り、最終的には端末内で動く軽さを目指す。利用者の音声が本プロジェクトに送られることはない。

## 評価手順（公開予定）
- 日本語が話せる公開 TTS 複数（声の複製を含む）と、LLM＋TTS の「会話する AI 電話役」。
- 人間側は台本読みと自由会話の両方。
- 全音声を 8kHz 相当に落とし、電話の圧縮（AMR-NB / 狭帯域 Opus）と雑音を通す。
- 調整に使う TTS と評価に使う TTS を分ける（未知の TTS で測る）。
- 公開する表: TTS 別・音質別の「AI と判定できた率」、人間側の「誤って AI と判定した率」。

## 既知の限界
- 受け身の痕跡検知は電話音質と合成音声の進歩で弱くなる。だから能動テストを足す。
- 能動テストはいたちごっこ。課題の族を増やし、実行時生成で対応する。
- 誤検知は人間関係を傷つける。断定しない設計で緩和するが、ゼロにはならない。
- 通話音声に触れる経路は OS や法制度の制約が大きい。採用側（通信事業者・端末メーカー）が最も自然に実装できる。
- **法制度は国で違う。** 本提案は端末内・自宅内で完結し、録音を外部に送らないので、日本・米国・EU のいずれでも採用しやすい位置にある。ただし通話録音の同意（米国の一部の州や EU 各国は相手の同意が要る）、生体情報の扱い（EU GDPR、米イリノイ州 BIPA など）、転送型にした場合の通信事業規制は採用側が各国で確認すること。EU AI 法と米 FCC の規則は「AI は名乗れ」を義務づけており、本提案の「名乗らない相手を疑う」作法の裏付けになる。日本にはこの義務がないため、技術での判定の比重が高い。

## 通信事業者・端末メーカーが考える必要のある課題（採用側への宿題）
この作法を網内や端末の標準機能にするとき、提案側では決められない論点を挙げる。

| 論点 | 何を決めるか | 備考 |
|---|---|---|
| 声の盗み取りの検知 | 短い無言の着信・同一発信元からの大量のワンギリを網内で検知し警告できるか | 既存の迷惑電話の判定と組み合わせる |
| 保留の実装 | 網内で発信者を保留に入れ、別の音声（課題）を流し、受ける側にだけ結果を返す経路 | 既存の保留音・ガイダンスの仕組みを流用できるか |
| 同意と通知 | 発信者に「確認中である」ことをどう告げるか。録音・解析の同意を誰がどの時点で取るか | 通話の片方の同意で足りるかは国・地域で異なる |
| 法制度 | 通信の秘密（電気通信事業法 4 条）との整理。解析を網内で行うことの可否、利用者の明示の同意の形 | 迷惑電話対策の既存の整理（発信番号の表示・国際電話の遮断）が参考になる |
| 誤検知の責任 | 「AI の可能性: 高」と出た相手が人間だったときの扱い。免責の書き方、利用者への説明 | 断定しない設計でも苦情は出る |
| 緊急通話 | 110・119 などへは適用しない。発信者が緊急の人間（病院・学校）だった場合の救済 | 事前の許可リスト |
| 発信者の自己申告 | AI が発信するときに「AI です」と名乗る仕組み（発信者属性の信号）。網をまたいで信頼できる電子署名の整備 | 米国 STIR/SHAKEN に相当する仕組みが日本にはない |
| 課題の文言と文化 | 高齢者・聴覚障害・外国語話者に対する課題の設計。怒らせない文言 | 課題の族ごとに代替手段（画面での確認など）を用意する |
| 更新の仕組み | 合成音声の進歩に合わせた痕跡モデルと課題の族の更新を誰が担うか | 反例の音声を集める共同の場が要る |
| 費用と料金 | 保留中の通話時間の課金、無料にするか | 詐欺対策として無料提供が望ましい |
| 相互運用 | 事業者をまたぐ通話で、どちらの網が判定を担うか。結果の受け渡しの形式 | 結果の表現（可能性・理由）を共通化する |
